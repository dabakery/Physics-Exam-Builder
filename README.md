# Physics Exam Builder

This repository is a modification of [https://github.com/Zhongzhou/ESTELA-physics-problem-bank](https://github.com/Zhongzhou/ESTELA-physics-problem-bank) that is tuned for regular and AP level high school Physics using a foundation of exam questions that I have written over time.

It holds isomorphic problem banks for introductory Physics, created with the assistance of
generative AI, and a web app that browses those banks, assembles an exam from them, and
exports it. The live corpus is 50 ready banks holding 780 questions, counted on 2026-08-28.

The bank structure supports conversion to QTI packages for use with Canvas. This fork does
not use Canvas, so the QTI zips are **not embedded by default.** Pass `--include-qti` to
`scripts/build_standalone_html.py` to embed them again. The "⬇ QTI" button in the app hides
itself when they are absent.

## Exam builder (web app)

**Live at [physics-exam-builder.pages.dev](https://physics-exam-builder.pages.dev/).**

A single, self-contained page for browsing the problem banks, assembling an exam, previewing
the rendered math, and exporting it. The problem banks are embedded directly in the page as a
base64 zip, unpacked in the browser. An internet connection is only needed for math rendering
(KaTeX), js-yaml, and JSZip, which load from CDN.

The published page is generated by
[`scripts/build_standalone_html.py`](./scripts/build_standalone_html.py) from the enhanced
template, and is written to `docs/standalone-enhanced.html`.

### Using the page

The left sidebar is for finding banks. The three filters narrow by course, then chapter, then
topic, and the Topic filter appears only when the selected chapter has subtopic folders under
it. Search matches bank titles, IDs, descriptions, learning objectives, and folder names, and
the question type chips narrow to banks that contain that type. The summary line above the
cards counts the banks, questions, and topics that are currently showing, so it moves as you
filter rather than describing the whole library.

Each card previews a question or two with the math rendered. **The card never shows an answer,
a solution, or the raw YAML,** so the page can be put in front of a class. Answer keys come
from the exporters and from quiz feedback, both of which are meant for the teacher or for a
student who has already answered.

The cart button in the top bar opens a drawer on the right that holds the cart and the Build
Exam panel. Set the number of versions there, then either take the quiz or open the Export
section for previews and downloads. The **Exam Title** field is worth setting before you
export, because it becomes the heading on every exam and key and the stem of every downloaded
filename.

### Export formats

| Format | Use |
|---|---|
| **`.md`** | **Preferred.** Import to Google Docs, then render the math with the *Auto-LaTeX Equations* add-on |
| Preview | In-browser render with KaTeX. Print or save as PDF from there |
| `.tex` | LaTeX source for each exam and answer key version |
| Bundle `.zip` | All versions and keys as `.md`, plus the figure files |
| `.doc` | Word, beta. Math fidelity is limited |

The Markdown path is the one to use for anything you intend to edit. Google Docs' Markdown
import has no math support, so `$…$` survives as literal text which can then be rendered as
math images by the [Auto-LaTeX Equations add-on](https://workspace.google.com/marketplace/app/autolatex_equations/850293439076).
**Turn on the add-on's single-`$` delimiter setting**, since the exporter emits single `$`
deliberately (see *Authoring rules* below).

### Interactive quiz mode

**Take Quiz** in the cart drawer turns the current cart into a quiz answered in the browser.
Submitting grades it and shows the `on_correct` / `on_incorrect` feedback the banks carry for
Canvas QTI, which nothing else in this app displays (the exporters and the bank browser read
only `feedback.general`).

A correct answer also releases the worked solution from `feedback.general`, marks the correct
option, and shows the expected numerical value. A wrong or blank answer gets the
`on_incorrect` hint and nothing else, so **Try again** stays worth doing. The student's own
selections stay on screen either way.

### Try again with a new set

**Try again** asks whether to repeat the same questions or draw a new set. A new set advances
the quiz version, which shifts every bank's window forward by the number of questions that
bank contributes. Each bank therefore moves through its own isomorphs in order and wraps at
the end, and banks of different sizes run out at different points.

The dialog reports what is actually available before you choose, for example "2 of 3
questions have a different version available. The other 1 would repeat." Once every version
has been used it says the new set would cycle back to questions already seen. **New set** is
only disabled when it would return an identical set, which happens when every bank is already
contributing all of its questions.

### Get help button

Each question can carry a **Get help** button that opens a Gemini Gem set up as a Socratic
Physics tutor. The button copies a prompt to the clipboard, shows a confirmation, and opens
the Gem in a new tab for the student to paste into.

To turn it on, set `TUTOR_URL` at the top of
[`frontend/exam-quiz.js`](./frontend/exam-quiz.js) to the Gem's public share URL. While that
constant is empty the button is not rendered, so the page never shows a link that goes
nowhere.

The copied text reads:

```
I need help with this Physics problem from AP Physics 2. The question is <question text>
```

The course name comes from the bank's course folder, and `<latex>` tags are converted to
`$…$` and `$$…$$` so the tutor parses the math. The correct answer is never included.

The paste step is required because Gemini has no supported URL parameter for pre-filling a
prompt, and `gemini.google.com` sends `x-frame-options: DENY`, so it cannot be embedded in a
frame either. Browser extensions that add `?prompt=` support exist, but relying on one would
mean every student needs it installed.

### What quiz mode grades

Quiz *vN* draws exactly the same questions, in the same order and with the same shuffled
answer options, as Exam *vN*, so it doubles as a self-check against a printed version.

| Question type | In quiz mode |
|---|---|
| `numerical` | Graded against `value`, honoring `tolerance` and `margin_type: percent`. Answers with no declared tolerance fall back to ±1%. Units typed after the number are ignored |
| `multiple_choice` | Graded, single selection |
| `multiple_answers` | Graded, exact set match with no partial credit |
| `categorization` | Graded. One dropdown per item asking which category it belongs to, with the full category descriptions listed above. All items must be placed correctly |

That covers every question type the banks currently use. As of 2026-08-28 the 50 ready and
deployed banks hold 356 numerical, 273 multiple choice, 82 categorization, and 69 multiple
answer questions.

Scope and limits, by design:

* **Practice, not assessment.** Nothing is saved, submitted, or collected, and a refresh
  discards the attempt. Use the exporters for anything that counts.
* **Enhanced build only.** `frontend/index.html` (the Tauri desktop entry) does not get
  quiz mode. Duplicating several hundred lines into it would double the maintenance cost
  described under *Two copies of the frontend* below for no benefit.
* Lives in [`frontend/exam-quiz.js`](./frontend/exam-quiz.js), a fork-local file with no
  upstream counterpart, so it cannot conflict on an upstream merge. It is inlined into the
  standalone build only when the template references it, which is the same conditional rule
  `exam-export-plus.js` already uses.

A desktop app (Tauri) also exists under `src-tauri/` and still builds on `v*` tags, but it is
no longer advertised on the site.

## What are isomorphic problem banks and how to use them.
### Isomorphic problems
The working definition of "isomorphic problems" are problems that have variations that are:
* More substantial than simply changing numbers or trivial replacement of nouns. 
* Involve at least one modification in the problem solution, such as changing a negative sign.
* Are considered to test the same set of learning objectives for the course, while not significantly changing difficulty (currently this is still a subjective call.)

### Isomorphic problem banks
An isomorphic problem bank is a collection of problems so that any two problems in one bank can be considered as isomorphs according to the above definition. These problem banks are dynamic and can be updated and extended.

### Recommended use of isomorphic problems banks
* Build several versions of the same exam at once, so that neighboring students answer
  different isomorphs of each question.
* Give a bank to students as practice, then draw the exam item from the same bank.
* Assign the quiz mode as practice, since it grades in the browser and gives the feedback
  written into the bank.
* Upload a bank to Canvas as a New Quiz item bank if you use Canvas. That path needs the QTI
  export, which is described in the creation workflow below.

|---|---|---|---|
| [PHY I Mechanics](./PHY%20I%20Mechanics/) | `PHY1` | 0 to 12, upstream's university sequence | 27 |
| [AP Physics 1](./AP%20Physics%201/) | `APP1` | 1 to 8 | 0, in progress |

**The unit folder number is what students see.** The exam builder shows each chapter folder name verbatim, so the number in the folder name is the unit number on the site. The two AP courses use the College Board unit numbers directly, and together they form one unbroken 1 to 15 sequence (AP Unit 1 Kinematics → `1_Kinematics`; AP Unit 9 Thermodynamics → `9_Thermodynamics`, whose subtopic folders are numbered `9.1`, `9.2`, and so on). HS Physics follows its own order, numbered from 1. `PHY I Mechanics/` is the exception and starts at 0, because upstream's unit 0 is a math review that comes before the course proper. Check the course's own `README.md` before assuming a folder number means the same thing in two places.


* Each course has a `Topics.csv` catalog of its units
* Each unit folder roughly corresponds to one unit of instruction. Each unit folder contains multiple problem bank folders.
    * Each problem bank folder contains the following components
        * A YAML file (.yml or .yaml). This contains the problem bank and problem bank meta-data, and is human-readable.
        * (Optional) A QTI file (.zip). This is the file that can be imported into CANVAS New Quiz Item Bank. 
        * (Optional) Either a Figure.zip or Image.zip file, or an image folder. This contains all the images used for each problem.
        * (Optional) Folders that contain other related meta-data or backup, older version yaml files.
    * The yaml and zip file, as well as the problem folder, are named according to the following naming convention:

            Subject-Unit-Abbreviation_of_title-mmddyy.yaml
            
            For example: PHY1-F-1DKINT-091525 corresponds to: Physics 1, Force, 1D Kinematics with Non-Constant Acceleration, created on 09-15-2025
*Note:* Some earlier folders have yet to be cleaned up.

## Authoring rules

Beyond the YAML schema in [`Templates/`](./Templates/), these rules come from how the
banks are actually rendered and exported. Breaking them mostly fails *silently*, since the
file downloads fine and the damage only shows up in Google Docs.

**Bank folders may sit one level deeper for a subtopic.** The sidebar filters
Course → Chapter → Topic, and that third level comes from the folder layout:

```
AP Physics 2/9_Thermodynamics/9.1_Kinetic Theory.../APP2-THM-KTTP-080926/…yaml   ← filterable
PHY I Mechanics/3_Forces/PHY1-F-OFKF-030625/…yaml                                ← flat, still fine
```

The level is optional. A bank directly under the chapter folder simply reports no subtopic
and renders exactly as before, so `PHY I Mechanics/` is left flat on purpose. The Topic dropdown
hides itself when the selected chapter has no subtopics.

**`status:` gates visibility.** Only `ready` and `deployed` are parsed by the builder, and
`draft` and `deprecated` are skipped entirely. New banks start as `draft` and stay invisible
until you flip them. Folders named `Old`, `Archive`, `Drafts`, `Figure Creation`, and the like
are skipped by the bundler, which is useful for parking work in progress.

**Write the description as a paragraph, then teaching notes.** The bank card clamps the
description to three lines, and it drops both an opening sentence that only restates the
course and topic number and everything from a `Teaching notes:` line onward. Search still
reads the whole field, so nothing is lost, but the three lines a student sees are the ones
that describe the Physics.

### Google Docs compatibility

**Always use `<latex>…</latex>`, never raw `$…$`.** Two upstream banks mix raw `$R/2$` and
`$\vec{L}$` in among the tags. Those spans bypass the exporter's escaping, so any backslash
command inside them is corrupted on import to Google Docs (`\,` arrives as a bare comma).
Only text inside `<latex>` tags is protected.

**Never put a literal `$` in question text.** The Auto-LaTeX add-on pairs delimiters
sequentially across the whole document, so one stray `$` inverts everything after it. The exporter warns on an odd delimiter count when you download, but the fix belongs in the bank. Write "5 dollars", not "$5".

**Write units as plain text *after* the closing tag.** The exporter pulls a trailing unit
into the math so the value and unit render as one equation:

```yaml
text: The required force is <latex>465.64</latex> N. Gravity is <latex>9.81</latex> m/s².
#     →  $465.64\ \mathrm{N}$        →  $9.81\ \mathrm{m}/\mathrm{s}^{2}$
```

Recognized units: `kg mol rad min Hz Pa km cm mm nm ms °C °F Ω N J W A V C K T L m s g °`,
with `·`, `*`, `/`, and exponents in either `m/s²` or `m/s^2` form. One parenthesised level is
handled too, so `J/(mol·K)` is absorbed the way the AP equation sheet writes it. Anything else,
"furlongs" for example, is simply left as prose, which is harmless and just unstyled.

**Don't leave a bare single-letter word immediately after a closing tag.** The unit
absorber cannot tell a unit from a variable there:

```yaml
the length <latex>x</latex> L away      # ✗ → $x\ \mathrm{L}$, L read as liters
the length (<latex>x</latex>) L away    # ✓ punctuation stops the absorber
the length <latex>x</latex> from L      # ✓
```

Put the variable inside the tag, or separate the two with punctuation.

### Other tips

**Figures** must be flat, since filenames in the zip have to match the YAML references
exactly, with no subfolders. They are *not* embedded in the Markdown export. It emits
`*[Figure: name.png]*` placeholders, and the image files come from the Bundle `.zip`.

**Record `generation prompts:` and `updates:`.** Upstream treats this metadata as required
for future expansion of a bank, and it is the only record of how the isomorphs were derived.

### Validating a bank

```bash
node scripts/validate_banks.js                  # all four courses
node scripts/validate_banks.js "AP Physics 2"   # one course, unit, or bank folder
node scripts/validate_banks.js --strict         # warnings fail too
node scripts/validate_banks.js --quiet          # only files with findings
```

The validator exits 1 on any error, so it drops into a pre-commit hook unchanged. It parses
with the same js-yaml build the page loads, vendored in `scripts/vendor/`, because the page
is the only parser whose opinion matters. PyYAML is YAML 1.1 and js-yaml is YAML 1.2, and
they disagree on real inputs. A distractor written `correct: no` is a string in 1.2, which is
truthy, so the option grades as correct on the site while PyYAML would call the file fine.

Each check mirrors a specific line of shipped code rather than a general idea of good YAML.
The checks that catch the most are a missing or misspelled `status:`, an odd number of `$`
characters, a figure reference that does not resolve, and the bare-letter-after-`</latex>`
trap above.

Three files in `PHY I Mechanics/` fail to parse and are skipped by the page without any
message, and one of them, `PHY1-F-CWDVF-10052025.yaml`, says `status: ready` but has never
appeared on the site because of its indentation. They are upstream files, so fixing them here
would conflict on every merge and they are left alone deliberately.

## Problem bank creation workflow
Follow this workflow to create an isomorphic problem bank. If you wish to directly use any of the problem banks, skip to step 5.

1. *Setup the problem folder*: 
    * Create a folder under the intended course and unit. You can give it a temporary name such as "Newton's Laws Problem Draft".
    * Copy the [Problem-bank-template.yaml](./Templates/Problem-bank-template.yaml) file into your new folder

2. Complete the yaml file with the assistant of GenAI
    * Plan and start your problem creation process with GenAI assistance. (for reference see: https://arxiv.org/abs/2508.14755, and also see the existing folders as examples) 
    * Format the generated problems in the format specified in [YAML_problem_types.md](./Templates/YAML_problem_types.md) and [YAML_formatting_prompt.md](./Templates/YAML_formatting_prompt.md)
    * Make sure to record each generation prompt. This metadata is critical for understanding the structure of the bank and any future expansion.
    * Name your problem bank following the comments in the template document.
    * Save AI-generated data tables or code snippets in a sub-folder for more consistent future expansion of the problem bank.

3. (Optional) Add the images
    * If your problem involves one or more images, store them in a folder or a zip file that contains no sub-folders.
    * The file names of image files should match the names used in the yaml file. 

4. Publish the bank to the site
    * Run `node scripts/validate_banks.js "<your course>"` and clear any errors.
    * Set `status: ready` in the bank's `bank_info:` block. A bank left as `draft` will not
      appear.
    * Commit and push to `main`. Cloudflare Pages rebuilds the page on every push, so the
      bank appears on the live site without any other step.

5. (Optional) Import into Canvas
    * This fork does not use Canvas, but the banks are still QTI-compatible and the upstream
      path works.
    * Upload the yaml to the yaml to QTI converter: https://canvas-lti.cdl.ucf.edu/yaml-to-qti/
      The converter is developed by the UCF Center for Distributed Learning. Currently it is
      available to UCF faculty only, but it is in code review to be made open-source. It
      returns the QTI package as a zip file for download.
    * In CANVAS, go to any course that has item banks enabled (this is the default).
    * Go to item banks from the side menu, create a new item bank with a placeholder name.
    * Open the problem bank, click the vertical ... menu in the upper-right corner, and select "Import Content".
    * Either select the QTI zip file or drag the zip file into the upload dialogue box on the screen.
    * Recommended to only use the problem banks with New Quiz, since traditional quiz does not handle question banks very well and can create many independent copies.
    * To have the app offer the QTI zips as downloads again, build with `--include-qti`.

## Building and deploying

### Building the page

```bash
python3 scripts/build_standalone_html.py \
  --template frontend/enhanced.html \
  --output   docs/standalone-enhanced.html \
  --courses  "HS Physics" "AP Physics 1" "AP Physics 2" "PHY I Mechanics"
```

The script is Python standard library only, on purpose, so the deploy needs no
`pip install`. It bundles the bank files into a base64 zip and inlines the JS modules the
template references.

`--courses` **defaults to `PHY I Mechanics` only.** A course folder that is not passed is
silently omitted, which is the most likely reason a new bank does not show up. Only the
enhanced page is built, since `docs/index.html` links to that page alone.

### Deploying (Cloudflare Pages)

| Setting | Value |
|---|---|
| Production branch | `main` |
| Framework preset | None |
| Build command | the build command above, on one line |
| Build output directory | `docs` |
| Build system version | v3 |
| Environment variables | none |

Two settings are worth stating plainly, because both have cost time here. **The build command
is load-bearing.** With it empty, Pages skips the build and publishes the repository root,
which serves every bank YAML at a public URL. And **do not set `PYTHON_VERSION`.** Each build
image ships one preinstalled Python, 3.13.3 on v3, and any other value makes the build compile
CPython from source before it starts. Nothing here needs a specific version, which is also why
the repository intentionally has no `.python-version`, `runtime.txt`, or `.tool-versions`.

`docs/standalone*.html` is gitignored, since Cloudflare regenerates it on every deploy and a
committed copy would only drift. Frontend changes reach the site by committing the source, not
the build output. The generated page was 9.06 MiB on 2026-08-20 against Cloudflare's 25 MiB
per-file limit, and images are what set that number, so keep generated figures compressed
before committing them.

### Two copies of the frontend

`frontend/index.html` and `frontend/enhanced.html` are about 90% the same file, roughly 280 of
1,400 lines differ. Upstream added `enhanced.html` as a copy of `index.html` with the export
section de-gated. `index.html` is the Tauri desktop entry, so its exporters are implemented in
Rust behind `window.__TAURI__`, while `enhanced.html` substitutes the client-side ones in
`exam-export-plus.js`.

**Shared UI changes, meaning CSS, the sidebar, the top bar, and the render functions, must be
made in both files.** Only the exporter rows, the quiz block, the default open state of the
Export disclosure, `initSourceUi()`, and the page `<title>` are legitimately per-file. A change
made in one file only may appear to do nothing, since the published page is built from
`enhanced.html`.

The two are not worth deduplicating. There is no bundler here by design, and both files are
upstream-maintained, so extracting a shared shell would conflict on every merge from upstream.

### Keeping up with upstream

```bash
git fetch upstream && git merge upstream/main
```

`origin` is this fork and `upstream` is the ESTELA repository. A merge will try to revert the
changes that make this fork what it is, so check after every sync: the repository URLs that
point at this fork in `exam-export-plus.js`, `docs/index.html`, `src-tauri/src/main.rs`, and
`bank-service/app.py`; the withheld answer keys in the bank preview; the cart drawer; and the
QTI default. `frontend/exam-quiz.js` has no upstream counterpart and cannot conflict.
